Architecture Skills vs MCP vs mods vs everything else

Which extension point?

Claude Code has about ten ways to change how it behaves. They overlap, and the names don't make the difference obvious. The short version: text that teaches Claude goes in CLAUDE.md or a skill, new abilities come from MCP, a separate worker is a subagent, a script on an event is a settings hook, and code inside the loop is a mod. A plugin is the box they ship in.

One job, five ways: "never run rm -rf"

The clearest way to feel the differences is to try the same job with each one and ask what it actually guarantees.

ApproachWhat it looks likeWhat it guarantees
CLAUDE.md"Never run rm -rf; ask me instead."Nothing. It's advice. Claude usually follows it, and a long session or an odd prompt can drift.
SkillA "safe cleanup" skill that explains alternativesNothing, and it only loads when the task looks like cleanup. The wrong tool for a prohibition.
Permission rule"deny": ["Bash(rm -rf:*)"]That pattern is refused. It's declarative and fast, and it misses rm -fr, rm -r -f and find … -delete.
Settings hookA PreToolUse script that parses the command and exits with a blockWhatever your script checks, in any language. It runs in parallel with other hooks and can't show UI. A managed one runs before any mod.
ModA tool.call guard with .catch, or one that holds the call and asks with $.ui.askWhatever your code checks, in a known order, with UI. It fails open without .catch. A worker crash loop unloads it.

In practice: the deny rule for the obvious spelling, a hook or mod for the rest, and a CLAUDE.md line so Claude doesn't try in the first place. Layers, not a winner.

Rules of thumb

  1. Start with text. If you keep pasting the same instructions, write a CLAUDE.md line (always relevant) or a skill (relevant to one kind of task). It's cheap, readable and easy to change.
  2. Need a new ability? MCP. If Claude must reach a system it can't reach today, that's a tool, and tools come from MCP servers. A mod can register a tool too, which is handy when the tool needs session state the mod already has.
  3. Need isolation? A subagent. A separate context for a big search or a review, possibly on a cheaper model. A mod can pin which model a subagent uses (agent.spawn) or hide an agent type (agent.offer).
  4. Need a guarantee? Rules first, then hooks or mods. Permission rules for patterns. A settings hook if you already have the script, or if you need it to run before any mod (managed). A mod if you need order, state, UI or to rewrite the event.
  5. Need to draw, or to run code on a command with no Claude turn? Only a mod can.
  6. Shipping several? A plugin. One install can bring a skill, an MCP server, a subagent and a mod that work together.

Where a decision model fits

Our sister site, Decision Tier, studies decision models: fast, typed judgments such as "is this command destructive?" with a probability attached. A decision model is a callee, not an extension point. In Decision Tier's words, mods and hooks call decision models; skills and CLAUDE.md teach Claude when to trust them.

  • From a mod or settings hook: a $.http.fetch in a guard, with a timeout and .catch failing closed. This is the hot path. See Mods meet the cascade.
  • As an MCP tool: only when you want Claude to choose to ask for a judgment. That's rarely what you want, because then the expensive tier decides when to consult the cheap one.
  • Never as a skill or subagent. A skill is instructions, not a judge, and a subagent is another LLM.
